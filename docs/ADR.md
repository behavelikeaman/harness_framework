# Architecture Decision Records

## 철학
MVP 속도 최우선. 외부 의존성 최소화. 작동하는 최소 구현을 선택한다. API 쿼터와 API 키 노출은 나중에 고치기 비싼 문제이므로 처음부터 지킨다.

---

### ADR-001: Next.js 15 App Router 선택
**결정**: Next.js 15 App Router + route handler를 백엔드로 사용한다. 별도 API 서버를 두지 않는다.
**이유**: YouTube API 키와 Anthropic API 키를 서버에서만 다뤄야 하는데, route handler를 쓰면 프론트와 한 프로젝트 안에서 이를 해결할 수 있다. Vite SPA로 가면 키 보호를 위해 별도 프록시 서버가 반드시 필요해진다.
**트레이드오프**: 순수 정적 배포가 불가능하고 Node 런타임이 필요하다.

### ADR-002: 데이터 저장소를 두지 않는다
**결정**: DB 없이 매 요청마다 YouTube API를 재조회하고, `lib/cache.ts`의 10분 TTL 메모리 캐시만 둔다.
**이유**: 채널 1회 분석이 3 units에 불과해 재조회 비용이 사실상 없다. 스키마·마이그레이션·ORM을 전부 생략하면 MVP가 며칠 빨라진다.
**트레이드오프**: 분석 이력 조회, 채널 성장 추이 비교가 불가능하다. 프로세스 재시작 시 캐시가 사라진다.

### ADR-003: quota 절약형 3-call 파이프라인
**결정**: `channels.list` → `playlistItems.list` → `videos.list` 순으로만 호출한다. `search.list`는 어떤 경우에도 호출하지 않는다.
**이유**: `search.list`는 호출당 100 units라 일일 한도 10,000 기준 하루 100회 분석이 끝이다. 3-call 파이프라인은 3 units이므로 같은 한도로 3,000회 이상 분석할 수 있다. 채널 핸들 해석도 `channels.list(forHandle=...)`로 대체 가능하다.
**트레이드오프**: 최근 업로드 50개만 볼 수 있고, "실제 유사 영상 검색" 기능을 포기한다. 그래서 추천은 실물 영상 검색이 아닌 AI 기획안 생성으로 간다(ADR-004).

### ADR-004: 추천은 Claude 구조화 출력으로 생성한다
**결정**: 상위 성과 영상의 제목·지표·태그를 `claude-opus-5`에 넘겨, zod 스키마로 강제된 구조화 출력(`messages.parse` + `zodOutputFormat`)으로 기획안 5개를 받는다.
**이유**: YouTube quota를 전혀 소모하지 않으면서 "왜 터졌는가 → 다음에 뭘 만들까"라는 사용자의 실제 질문에 답한다. 프리텍스트를 정규식/JSON.parse로 뜯는 방식은 파싱 실패가 런타임 버그가 되므로 배제한다.
**트레이드오프**: Anthropic API 비용이 발생하고, 추천이 실제 검증된 영상이 아닌 생성된 가설이다. 그래서 각 기획안에 근거 영상 ID를 반드시 붙여 사용자가 검증할 수 있게 한다.

### ADR-005: 성과 기준선은 평균이 아닌 중앙값
**결정**: `performanceRatio`의 분모를 채널 조회수의 **중앙값**으로 하고, Shorts와 롱폼의 중앙값을 각각 따로 계산한다.
**이유**: 바이럴 영상 한 편이 평균을 끌어올려 "모든 영상이 평균 이하"로 보이는 왜곡을 막는다. Shorts는 롱폼과 조회수 스케일 자체가 달라 한 기준선에 섞으면 롱폼이 전부 저성과로 찍힌다.
**트레이드오프**: 표본이 적은 채널(영상 5개 미만)에서는 중앙값도 불안정하다. MVP에서는 감수한다.
